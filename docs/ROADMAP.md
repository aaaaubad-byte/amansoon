# خارطة طريق تطوير AMAN

## طريقة قراءة الخطة

كل مرحلة لها مخرجات واضحة ومعايير قبول. لا تنتقل المرحلة إلى `مكتملة` إلا بعد تنفيذ المخرجات وتشغيل الاختبارات وتحديث سجل التسليم. إذا توقفت الحصة أو انتقل العمل إلى حساب آخر، يبدأ التنفيذ من أول مرحلة غير مكتملة.

## المرحلة 0: تهيئة تطبيق Flutter وSupabase

**الحالة: قيد التنفيذ — الأساس البرمجي مكتمل، والتحقق النهائي ينتظر بيئة Flutter/Android.**

**الهدف:** إنشاء أساس قابل للاستمرار.

المخرجات:

- مستودع Git منظم.
- مشروع Flutter بصيغة Android APK.
- دعم العربية وRTL وMaterial 3.
- ربط Supabase Auth وSupabase PostgreSQL.
- إعداد متغيرات `SUPABASE_URL` و`SUPABASE_ANON_KEY` فقط داخل البيئة.
- مجلد هجرات SQL وسياسات RLS.
- توثيق تشغيل المشروع وبناء APK.

معيار القبول: يستطيع مطور جديد تشغيل Flutter وربطه بمشروع Supabase مخصص للتطوير وبناء APK تجريبي باتباع README فقط.

المنجز في جلسة 2026-09-19:

- إنشاء `aman_app/pubspec.yaml` وطبقات الإعداد والثيم وعميل Supabase.
- تنفيذ تسجيل عميل جديد، تسجيل الدخول، تسجيل الخروج، وقراءة الدور من `public.profiles`.
- إضافة واجهة عربية RTL ومسار أولي منفصل للعميل والمدير.
- توثيق أوامر التشغيل والبناء باستخدام `--dart-define` دون أسرار داخل Git.
- تعذر تشغيل `flutter test` و`flutter build` لأن Flutter SDK وAndroid SDK غير متوفرين في بيئة التنفيذ الحالية.

## المرحلة 1: مخطط Supabase والمصادقة

المخرجات:

- هجرات SQL للجداول الأساسية.
- `profiles` وربط المستخدمين بـ Supabase Auth.
- دور العميل ودور المدير.
- تسجيل وإنشاء جلسة وتسجيل خروج.
- سياسات RLS واختبارات العزل.
- RPC محمية للعمليات الحساسة الأولية.

معيار القبول: يمكن إنشاء عميل وتسجيل دخوله من APK، ولا يستطيع العميل قراءة بيانات عميل آخر أو تنفيذ عملية إدارية.

## المرحلة 2: الشركات والأرقام والباقات وطرق الدفع

**الحالة: قيد التنفيذ — إدارة الشركات والباقات وبدء طلب الحماية منفذة، وواجهة طرق الدفع الإدارية ومراجعة الطلبات ما زالت متبقية.**

المخرجات:

- CRUD لشركات الاتصالات.
- CRUD للباقات مرتبطة بشركة واحدة.
- CRUD لطرق الدفع.
- إضافة العميل لأرقامه.
- منع تكرار الرقم.
- عرض الشركات والباقات الفعالة والظاهرة فقط للعميل.
- واجهات الإدارة والعميل لهذه الوظائف.

معيار القبول: لا يمكن اختيار باقة من شركة مختلفة، وتعطيل الباقة يمنع استخدامها في طلب جديد دون حذف السجل التاريخي.

## المرحلة 3: طلبات الحماية

**الحالة: قيد التنفيذ — إنشاء الطلب ومراجعة المدير والقبول/الرفض المعاملي وقائمة إشعارات العميل منفذة، وتفاصيل الإشعارات الإدارية والجدولة ما زالت متبقية.**

المخرجات:

- معالج طلب حماية متعدد الخطوات.
- تخزين Snapshots للقيمة والمدة.
- إدخال رقم المرجع.
- قائمة العميل وتفاصيله.
- قائمة المدير ومراجعة الطلب.
- قبول ورفض مع سبب إلزامي.
- إشعارات أساسية.
- Audit Log.

المنجز الإضافي في جلسة 2026-09-19:

- عرض إشعارات العميل المحفوظة فعليًا في `notifications`.
- تحديد الإشعار كمقروء مع احترام عزل RLS للمستلم.

معيار القبول: القبول ينشئ حماية ومهمة أولى في Transaction، والرفض لا ينشئ حماية أو مهمة.

## المرحلة 4: الحمايات

**الحالة: قيد التنفيذ — قائمة حمايات العميل وبياناتها التاريخية وسجل العمليات الإداري منفذة، وتفاصيل المدير ومنع التعارض واختبارات E2E متبقية.**

المخرجات:

- قائمة حمايات العميل.
- قائمة حمايات المدير.
- تفاصيل الحماية.
- حساب البداية والنهاية.
- تحديث حالة الرقم إلى محمي.
- منع حماية مكررة.
- عدم تأثر الحماية بتعديل الباقة لاحقًا.

معيار القبول: بيانات الحماية السابقة ثابتة تاريخيًا، والعلاقات صحيحة في قاعدة البيانات.

## المرحلة 5: إعدادات المهام والمهام التشغيلية

**الحالة: قيد التنفيذ — إعدادات الشركة الأساسية وعرض المهام وإكمالها منفذة، والتصنيفات وأنواع المهام والإشعارات الزمنية ما زالت متبقية.**

المخرجات:

- إعدادات مستقلة لكل شركة.
- تصنيفات وأنواع المهام.
- مبلغ المهمة وفترة التكرار وأيام التنبيه.
- إنشاء المهمة الأولى.
- أقسام قادمة وقريبة واليوم ومتأخرة ومكتملة وملغاة.
- إكمال المهمة.
- إنشاء المهمة التالية.
- منع الإكمال المكرر.

معيار القبول: إكمال المهمة ينشئ دورة تالية واحدة فقط وفق إعدادات شركة الحماية، ولا يستخدم إعدادات شركة أخرى.

## المرحلة 6: الجدولة والتنبيهات

المخرجات:

- Worker مستقل أو Scheduler.
- تحديث الحالات الزمنية.
- إشعارات المدير للمهام القريبة والمتأخرة.
- إشعارات العميل المرتبطة بالحماية وفق السياسة المعتمدة.
- حماية التكرار في Jobs.

معيار القبول: تشغيل Job أكثر من مرة لا ينشئ إشعارات أو مهام مكررة.

## المرحلة 7: الإعدادات والتقارير والتقوية

المخرجات:

- إعدادات النظام والحماية والإشعارات.
- لوحة مؤشرات المدير.
- تحسين البحث والتصفية.
- نسخ احتياطي ومراقبة أخطاء.
- مراجعة أمان وصلاحيات.
- اختبار E2E شامل.
- توثيق النشر والاسترجاع.

معيار القبول: يستطيع فريق آخر نشر نسخة Staging واستعادة قاعدة البيانات وفق وثائق المشروع.

## المرحلة 8: بناء APK والإصدار

**الهدف:** إخراج نسخة Android قابلة للتثبيت والتسليم.

المخرجات:

- إعداد Android application ID واسم التطبيق وأيقونته.
- ربط بيئة الإنتاج أو Staging حسب نوع الإصدار.
- إنشاء APK تجريبي Debug أو Release للاختبار.
- اختبار التثبيت والتسجيل والاتصال بـ Supabase على هاتف فعلي.
- إنشاء نسخة Release موقعة عند توفير Keystore.
- حفظ رقم الإصدار وسجل التغييرات.
- رفع ملف APK أو رابط تنزيله خارج Git إذا كان حجم الملف مناسبًا لذلك.

معيار القبول: يثبت APK على هاتف Android، يفتح دون أخطاء، ويتصل بقاعدة amansoon ويجتاز التدفقات الأساسية للعميل والمدير.
