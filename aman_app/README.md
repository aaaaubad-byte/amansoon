# AMAN Android App

تطبيق Flutter عربي وRTL للعميل والمدير، متصل بـ Supabase عبر المفتاح العام فقط.

## المتطلبات

- Flutter SDK حديث متوافق مع Dart 3.3 أو أحدث.
- Android SDK لبناء APK.
- مشروع Supabase تطويري يحتوي على جدول `profiles` والهجرات المطبقة.

## التشغيل

لا تضع المفاتيح في Git. مررها وقت التشغيل أو البناء:

```bash
flutter pub get
flutter run \\
  --dart-define=SUPABASE_URL=https://YOUR_PROJECT.supabase.co \\
  --dart-define=SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
```

ولبناء APK تجريبي:

```bash
flutter build apk --debug \\
  --dart-define=SUPABASE_URL=https://YOUR_PROJECT.supabase.co \\
  --dart-define=SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
```

يمنع منعًا تامًا وضع `service_role` key داخل APK أو ملفات المشروع.

## التدفق المنفذ

- تسجيل عميل جديد عبر Supabase Auth مع `full_name` و`phone` في metadata.
- تسجيل الدخول بالبريد وكلمة المرور.
- قراءة ملف المستخدم من `public.profiles` بعد تسجيل الدخول.
- توجيه أولي بحسب الدور `customer` أو `admin`.
- تسجيل الخروج.

## طبقة الشركات والأرقام

أضيف `CatalogRepository` للتعامل مع قاعدة البيانات الفعلية عبر RLS:

- قراءة شركات الاتصالات الفعالة والمرئية فقط.
- قراءة الباقات الفعالة والمرئية التابعة للشركة المحددة فقط.
- قراءة أرقام المستخدم الحالي فقط.
- إضافة رقم جديد باسم المستخدم الحالي؛ وتترك قاعدة البيانات منع التكرار والتحقق من الملكية.

لا تستخدم هذه الطبقة مفتاح `service_role` ولا تعتمد على معرف العميل القادم من الواجهة لتحديد المالك.

واجهة `أرقامي` تستخدم هذه الطبقة مباشرة، وتعرض حالة الرقم إن كان محميًا أو غير محمي. لا تعرض الواجهة نجاح الإضافة إلا بعد نجاح الإدخال في PostgreSQL.

## لوحة المدير

تظهر لوحة إدارة الكتالوج للمستخدم الذي يحمل الدور `admin` من جدول `profiles`، وتتيح:

- إضافة وتعديل وتعطيل شركات الاتصالات.
- إضافة وتعديل وتعطيل باقات كل شركة.
- عرض الحالة الحالية للشركات والباقات.

التعطيل يستخدم الحالة المنطقية `inactive` بدل حذف السجل، حتى تبقى العلاقات التاريخية صالحة. تعتمد كل العمليات على سياسات RLS الإدارية في Supabase.

## طلب الحماية

يحتوي التطبيق الآن على معالج عميل من أربع خطوات:

1. اختيار رقم غير محمي.
2. تحميل باقات الشركة المرتبطة بالرقم فقط.
3. اختيار وسيلة دفع فعالة ومرئية.
4. إدخال رقم المرجع وإرسال الطلب إلى `protection_requests`.

تُحفظ قيمة الباقة ومدتها كـ snapshot وقت الإرسال، ولا تعرض الواجهة نجاحًا إلا بعد نجاح الإدخال في قاعدة البيانات.

لوحة المدير تحتوي على شاشة مراجعة الطلبات قيد المراجعة. القبول والرفض ينفذان عبر دوال PostgreSQL محمية؛ القبول ينشئ الحماية والمهمة الأولى وسجل التدقيق والإشعار في معاملة واحدة، والرفض يتطلب سببًا إلزاميًا.

تتضمن واجهة العميل شاشة `طلباتي وحماياتي` لعرض الطلبات وحالاتها والحمايات الفعلية وتواريخ انتهائها من Supabase. لا تعرض الشاشة مهام التشغيل الداخلية للعميل لأن سياسة RLS الحالية تقصرها على المدير.

تحتوي لوحة المدير على شاشة المهام التشغيلية. إكمال المهمة يتم عبر RPC محمية داخل معاملة، وتُنشأ الدورة التالية مرة واحدة فقط وفق إعدادات الشركة، مع منع الإكمال المكرر.

تدعم شاشة المهام الآن حقول تصنيف المهمة ونوعها، مع تصفية القائمة حسب الحالة. وتعرض لوحة العميل عدد إشعاراته غير المقروءة قبل فتح شاشة الإشعارات.

يمكن للمدير تشغيل تحديث الحالات الزمنية من شاشة المهام. يستدعي التطبيق دالة PostgreSQL محمية `refresh_operational_task_statuses` لتصنيف المهام القابلة للتشغيل إلى قادمة أو قريبة أو اليوم أو متأخرة، مع استثناء المهام المكتملة والملغاة.

وتحتوي لوحة المدير أيضًا على شاشة إعدادات المهام لكل شركة، وتشمل مبلغ المهمة، مدة التكرار، قاعدة استحقاق المهمة الأولى، وعدد أيام اعتبار المهمة قريبة.

تتضمن لوحة المدير شاشة وسائل الدفع لإضافة وتعديل وتفعيل وتعطيل المحافظ والبنوك والصرافات. التعطيل منطقي، ووسائل الدفع غير الفعالة لا تظهر للعميل.

تتضمن لوحة المدير شاشة سجل العمليات لقراءة العمليات الحساسة الأخيرة من `audit_logs`. القراءة مقيدة بسياسة `audit_admin_access` التي تتحقق من دور المدير داخل قاعدة البيانات.

تتضمن لوحة المدير أيضًا قائمة حمايات العملاء. تقرأ الشاشة الحمايات من جدول `protections` وتعرض الرقم والقيمة والمدة وتاريخ الانتهاء والحالة، بينما تفرض قاعدة البيانات سياسة `protections_customer_access` التي تسمح للعميل بسجلاته وللمدير بالسجلات الإدارية.

تتضمن لوحة المدير شاشة إدارة المستخدمين لعرض ملفات `profiles`، والتصفية حسب الدور والحالة، وتفعيل أو تعطيل الحساب منطقيًا. لا تسمح الواجهة بتعديل الأدوار، وتمنع تعطيل حساب المدير الحالي أثناء استخدامه. تعتمد العمليات على سياسات `profiles_select_self_or_admin` و`profiles_update_self_or_admin` الفعلية.

تتضمن لوحة العميل شاشة الإشعارات لقراءة إشعاراته من جدول `notifications` الفعلي، وتحديد الإشعار كمقروء عند فتحه. يعتمد الاستعلام على `recipient_id` للمستخدم الحالي، وتظل صلاحية القراءة والتحديث محكومة بسياسات RLS.

إذا لم تُمرر متغيرات البيئة، يعرض التطبيق شاشة إعداد بدل إظهار نجاح وهمي أو محاولة اتصال غير مهيأة.
